## 0. 結論（確定）

**品番取引先マスタの登録漏れが原因です。**

2026/07 から品番 `6143190K00` ほか4品番の納入先が **1048（アキタ株式会社）** になっていましたが、
`品番取引先マスタ (品番, 取引先=1048, 受入=01)` が未登録でした。

その状態で 2026/08/05 10:16 に売上実績処理が実行され、
**契約先=NULL / 締日=NULL / 金額=0 の売上実績行が 25件**作成されました。

マスタは同日 10:56 に登録されましたが、**再処理してもこの25件が削除されない**ため、
同じ主キーで再登録しようとして PRIMARY KEY 違反になっています。

**残骸25件を手動削除してから再処理すれば復旧します。**（[復旧手順SQL_202607.sql](復旧手順SQL_202607.sql)）

## 2. なぜ「マスタを直したのに再処理で直らない」のか

これが本件の核心です。

### 2-1. 契約先NULL行は削除条件から外れる

`売上実績作成` の再処理DELETE:

```sql
DELETE 売上実績テーブル
 WHERE 実績年月 = @JYM
   AND ISNULL(契約先,'') LIKE @JTORCD          -- 契約先NULL → '' と評価される
   AND ISNULL(締日,0) >= @SSHIME               -- 締日NULL  → 0  と評価される
   AND ISNULL(締日,0) <= @ESHIME
   AND 入力区分 = ''
```

| 画面の指定 | @JTORCD / 締日範囲 | 契約先NULL行(契約先''・締日0)は消えるか |
|---|---|---|
| 契約先=**1048** | `'1048%'` | `'' LIKE '1048%'` → **消えない** |
| 締日=**個別31** | 31〜31 | `0` は範囲外 → **消えない** |
| 契約先=未指定・締日=全て | `'%'` / 0〜99 | 消える |

問合せは「対象の契約先の売上実績処理」なので、**契約先1048を指定して再処理**されているはずです。
その場合、残骸25件は**絶対に削除されません**。

### 2-2. 一方でカーソルは同じ出荷行を拾う

マスタが登録済みの今、カーソル側は:

```sql
AND ISNULL(HT.契約先,'') LIKE @JTORCD    -- '1048' LIKE '1048%' → TRUE
AND ISNULL(TR.締日,0) >= @SSHIME ...     -- 31 → 範囲内
AND ( ISNULL(実績年月,'') = '' OR ISNULL(実績年月,'') = @SYORI )   -- 202607 で一致
```

→ 出荷 (1196362, 3) が処理対象になります。

### 2-3. 集計判定も効かない

```sql
SELECT @SAVE_KANRINO = 検収管理NO FROM 売上実績テーブル
 WHERE 実績年月='202607' AND 品番='6143190K00' AND 納入番号='R1970'
   AND 契約先 = @HT_KTORCD   -- 今は '1048'。残骸行は 契約先=NULL なので一致しない
   ...
```

残骸行は契約先がNULLのため見つからず、`@SAVE_KANRINO = 0` → **INSERT 経路**へ。

### 2-4. 結果

```
INSERT INTO 売上実績テーブル (検収管理NO, 検収管理行NO, 実績年月, ...)
VALUES (1196362, 3, '202607', ...)
        ↓
残骸行と同じ主キー → PRIMARY KEY 違反
```

**「消せないのに作りに行く」というデッドロック状態**です。何度再処理しても同じ場所で止まります。

## 5. 金額への影響

**PK違反で止まっていること以上に、金額の誤りが問題です。**

契約先がNULLだと取引先マスタも引けず、`@TR_TANI`（計算単位）が NULL になります。
すると金額計算の `IF @TR_TANI = 0/1/2/3` がすべて UNKNOWN となり、`@KIN` が **0 のまま**INSERT されます。

- ⑱: 契約先NULL 25件は **全件 金額0**（本来は単価×納入数）
- ⑱の単価×納入数を行別に切上げ（計算単位=1）した合計は **124,429円**（単純合計 124,415.3円）
- ㉓: 契約先1048 の当月計上は現在 **14件・10,133,730円**

25件の (品番, 納入番号, 検収年月日, 単価) はすべて異なるため、伝票単位集計でまとまることはなく、
復旧後は **25件がそのまま計上**されます（⑱の一覧より確認済み。㉚で再確認可）。

> **⚠ ただし「1048 が 14件 → 39件になる」とは断定できません。**
> ㉓の 1048 の 14件・10,133,730円 には**手入力行（入力区分='1'）が含まれている可能性が高い**ためです
> （⑦の手入力合計 19件・10,092,031円 と金額が近接）。
> 自動作成分が本来何件あるべきかは、㉔で内訳を確認してから確定します。

> なお ㉓ では 1046 に1件、1051 に1件、1054 に2件、**契約先ありで金額0**の行があります。
> こちらは契約先NULLとは別要因（単価0や納入数0など）の可能性があり、**未調査**です。
> 復旧後に別途ご確認ください（復旧手順SQL STEP4-4）。

## 6. 売上明細の欠落について（副次的な不具合）

⑲で 入力区分`''` の明細欠落が **4件**ありました（`'1'` の19件は手入力行で明細を持たない仕様のため正常）。

原因は `売上実績作成` の次の分岐です。

```sql
IF (SELECT COUNT(*) FROM 売上実績テーブル          -- ← 売上実績テーブルを見て
      WHERE 検収管理NO=@KN_KNO AND 検収管理行NO=@KN_KNGYO AND 実績年月=@JYM) <> 0
   BEGIN
      UPDATE 売上明細テーブル SET ... , 契約先 = @HT_KTORCD , ...   -- ← 売上明細テーブルを更新
   END
ELSE
   BEGIN
      INSERT INTO 売上明細テーブル ...
   END
```

**存在確認の対象が「売上実績テーブル」なのに、更新対象は「売上明細テーブル」**です。

再処理のたびに次が起きます。

1. 残骸（売上実績）が存在 → UPDATE 分岐へ
2. 売上明細の 契約先 が NULL → **'1048' に更新される**
3. 次の再処理の DELETE（`契約先 LIKE '1048%'`）で **売上明細だけが削除される**
4. 売上実績の残骸は契約先NULLのまま → **明細だけ欠落**

**再処理を繰り返すほど欠落が増えます。**（現在4件）
残骸を削除すれば解消しますが、プログラム側の修正も推奨します。

> **この説明は「コード上そうなる」ことと「欠落4件がある」ことの整合であり、直接の裏取りはまだです。**
> 欠落している4件が契約先NULLの25件に含まれていれば裏取りできます（㉘で確認）。
> テーブル取り違え自体はコードを読めば明らかな不具合であり、こちらは確定です。

### 8-1. 運用（すぐできる）

**毎月の締め処理前に、品番取引先マスタが引けない出荷を洗い出す**
→ 復旧手順SQL の STEP5 をそのまま流用できます。
　 新規品番・納入先変更のたびにマスタ登録漏れが起きうるため、チェックの仕組み化を推奨します。

### 8-2. プログラム改修

| 案 | 内容 | 規模 | 優先度 |
|---|---|---|---|
| **案1** | **契約先が引けない出荷を処理対象から除外し、事前に一覧表示**する（売上単価未決ワークと同じ仕組み）。金額0での誤計上と残骸生成を根本から防ぐ | 中 | **最優先** |
| **案2** | 再処理DELETEの条件から `ISNULL()` による取りこぼしをなくす（契約先NULL行も削除対象に含める） | 小 | **高** |
| **案3** | 集計判定の NULL 比較を修正（`契約先 = @HT_KTORCD` → `ISNULL(契約先,'') = ISNULL(@HT_KTORCD,'')`）。売上実績・売上明細の伝票単位／月単位すべての分岐 | 小 | 高 |
| **案4** | 売上明細の存在チェックのテーブル取り違えを修正（第6章） | 小 | 高 |
| **案5** | `売上実績作成` のトランザクションを復活（2011/02/01 に「テスト用」でコメントアウトされたまま） | 小 | 中（性能影響の事前確認要） |
| **案6** | CXU0110 のエラー処理を改善し、ストアドのエラー内容を画面に表示する（実行時エラー91を出さない） | 小 | 中 |

**案1＋案2** の組合せで、「マスタ漏れがあっても壊れない・直せる」状態になります。
